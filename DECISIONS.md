# Decisions

## Architectural & Technology Decisions (already made)

- **Frontend framework:** Next.js (React) with TypeScript – defined in PRD section _Recommended Technical Architecture_.
- **Design system:** Custom NeoPOP‑inspired design system, built on top of NeoPOP components.
- **Styling:** Tailwind CSS with custom design tokens.
- **Animation library:** Framer Motion / Motion as specified in PRD.
- **Backend / data store:** Supabase PostgreSQL with pgvector for vector search (PRD §51). No Pinecone initially.
- **LLM provider:** Google Gemini API (PRD §49). Wrapped behind an `LLMProvider` abstraction.
- **Authentication (admin‑only):** Clerk **or** Supabase Auth – decision pending (see _Open Decisions_).
- **Hosting:** Vercel for the Next.js app, Cloudflare for DNS and edge caching (PRD §82).
- **Version control:** GitHub repository (PRD §102).
- **CI/CD:** GitHub Actions (PRD §104 – unit, integration, e2e tests).
- **Analytics:** PostHog (free tier) for event tracking (PRD §78).
- **Monitoring:** Sentry (optional, free tier) for error tracking (PRD §79).
- **Caching / rate limiting:** Upstash Redis **optional** – not required for MVP (PRD §53 – optional).
- **No CMS:** Content managed via version‑controlled JSON/Markdown files (PRD §55).
- **No Kubernetes / microservices:** Avoided per PRD _Non‑Goals_ and _Simplification Rule_.
- **Free‑tier focus:** All services chosen to stay within free tier limits (PRD §83).
- **Privacy & security:** Phone number redaction, PII detection, prompt‑injection guardrails, output validation (PRD §§36‑40, §80).
- **Accessibility target:** WCAG 2.2 AA (PRD §71).
- **Performance targets:** LCP < 2.5 s, CLS < 0.1, INP < 200 ms (PRD §74).

## Decisions (M13 – AI Knowledge Base)

- **The similarity search runs in the database:** PostgREST cannot order by a vector distance, so the search is a `match_knowledge_chunks` function. That keeps the HNSW index usable, keeps the classification filter where it cannot be bypassed, and avoids sending every embedding over the wire on each question.
- **The search function is revoked from the public roles:** PostgreSQL grants execute on a new function to `PUBLIC`, so the grant has to be revoked explicitly. Only the service role key, which bypasses row level security, may call it.
- **The similarity threshold was measured, not guessed:** The default of 0.55 comes from scoring the live knowledge base with professional and off-topic questions. Professional questions scored between 0.66 and 0.75 and off-topic questions between 0.48 and 0.57, so 0.55 keeps every relevant chunk while dropping about 92% of the off-topic ones. The guardrails of M13.07 own the final decision on an off-topic question, and the threshold should be re-measured once they exist.
- **A question is embedded with the retrieval task type:** The stored chunks were embedded with `RETRIEVAL_DOCUMENT`. A question is embedded with `RETRIEVAL_QUERY`, which is what the Gemini embedding models expect for a query.
- **Each text is sent as its own content object:** The Gemini SDK reads an array of plain strings as one content with several parts, so a batch of twenty texts returned a single embedding and the rest came back empty. Sending `[{ parts: [{ text }] }]` per text returns one embedding per text. A test asserts the shape of the request so this cannot silently break again.
- **A pgvector column is read back as a string:** PostgREST returns the vector as text such as `[0.1,0.2]`, not as an array of numbers. Anything that reads an embedding has to parse it.
- **Embedding generation is a separate step from ingestion:** The ingestion pipeline writes chunks with a null embedding and a separate backfill job fills them in. This keeps a Gemini outage from failing a knowledge base ingest, and it means the two concerns can be retried independently.
- **The Gemini SDK is used through thin adapters:** `src/lib/gemini.ts` is the only module that imports `@google/genai` for embeddings. It returns plain numbers and raises `GeminiApiError` with a status code, so no SDK type reaches the rest of the code. M13.06 added the second adapter, `src/lib/llm/geminiProvider.ts`, which is the only module that imports the SDK for generation.
- **Embeddings are normalised before they are stored:** Gemini truncates a vector when a smaller output dimension is requested, and `gemini-embedding-001` does not re-normalise the truncated result. Cosine similarity compares direction, so both sides of a comparison have to be unit length. The service normalises every vector and rejects one whose magnitude is zero.
- **The embedding model is asked for 768 dimensions explicitly:** The model returns 3072 by default, which the `vector(768)` column would reject. 768 is also at or below the 2000 dimension ceiling for indexing a pgvector `vector` column.
- **Retries only cover failures that can succeed on a second attempt:** Rate limits, timeouts and server errors are retried with exponential backoff. A rejected request or an invalid key fails the same way every time, so it is reported straight away.
- **The embedding service does not need the environment to be imported:** The Gemini module is loaded on demand, so the service can be imported and tested without a complete environment.
- **Knowledge base schema (before first deployment):** The initial migration was corrected while it had never been applied to a live database, which was the cheapest moment to do it.
  - *Embedding size stays at 768.* `gemini-embedding-001` returns 3072 dimensions by default, so the embedding service has to ask for 768 explicitly. 768 also has to stay at or below 2000, the ceiling for indexing a pgvector `vector` column.
  - *HNSW instead of IVFFlat.* IVFFlat clusters the rows that exist when the index is built. On a fresh table it would have been created with no usable cluster centres, and pgvector expects IVFFlat indexes to be rebuilt after the data is loaded. HNSW has no training step, so it works on an empty table and stays correct as rows are inserted.
  - *Row level security is enabled.* Without it the tables are readable through the public API with the anon key, which would expose every classification and bypass the filtering the pipeline applies. The pipeline writes with the service role key, which bypasses row level security.
- **Embedding model comes from the environment:** PRD §49 requires that no application code depends on Gemini specific details, so the embedding model name is a configuration value (`GEMINI_EMBEDDING_MODEL`) rather than a constant in the code.
- **Document identity and incremental updates:** A knowledge document is identified by its source type and title, which is unique within each source. Re-running the pipeline compares the rebuilt content with the stored content: an unchanged document is left untouched, and a changed document is updated in place with a new version and its chunks are replaced. This makes the pipeline idempotent and gives the versioning requirement something to act on. Two entries that share a title are disambiguated with a numeric suffix so neither is lost.
- **The store is injected into the pipeline:** `ingestKnowledgeSources` accepts a `SupabaseClient` and only falls back to the service role client when none is given. That lets the whole pipeline run against an in-memory double in CI, which is what PRD §104 asks for when it says to mock external services.
- **Markdown knowledge sources:** PRD §33 lists sources that are not structured data, such as public articles and approved interview talking points. These live as markdown files with a frontmatter block under `knowledge/`, and only that directory is ever read, so the pipeline never ingests arbitrary files from disk. The folder ships with a README documenting the format, which is excluded from ingestion.
- **Testing framework:** Node's built-in test runner (`node --test`) with `node:assert`. No test framework dependency is added. Node 24+ (the CI runner's `lts/*`) strips TypeScript types natively, so `.ts` sources run as-is. Test files use the `.test.mts` extension so they are always ESM, and `npm test` passes `--disable-warning=MODULE_TYPELESS_PACKAGE_JSON` to keep the output clean without adding `"type": "module"` to `package.json` (which would break the CommonJS `src/lib/env.js` used by `npm run env:check`). Playwright remains the choice for end-to-end tests per PRD §104.
- **Test placement and isolation:** Unit tests sit next to the module they cover and are picked up by the runner's default discovery glob. Modules that must be free of side effects to be testable are kept import-free — `src/lib/knowledge/chunking.ts`, `pii.ts` and `metadata.ts` have no imports at all, and `parseGitHubUrl` was moved into its own `src/lib/githubUrl.ts` for the same reason. Files loaded by the Node test runner must use erasable TypeScript syntax only: no parameter properties, enums or namespaces.
- **Environment validation during tests:** `src/lib/env.ts` validates every server-side variable at module evaluation time and throws when one is missing. Tests that import a module depending on it set placeholder values before a dynamic import, so the CI runner needs no `.env` file and production validation stays strict.
- **Typed Supabase insert payloads:** Writes use `KnowledgeDocumentInsert` / `KnowledgeChunkInsert` (the row types minus the database-generated `id`, `created_at` and `updated_at` columns) instead of casting partial objects to the full row type. The pipeline previously inserted a fixed all-zeros UUID as the chunk `id`; because `id` is the primary key, the second chunk of the first document would have collided. Letting the database generate `id` and `created_at` is both correct and type-safe.
- **Ingestion functions are typed against the source data models:** Every `process*` function accepts the exported interface from its `src/data/*` module (e.g. `Project`, `CertificationEntry`) rather than `any`. Field-name drift between the pipeline and a data model now fails at compile time instead of silently producing empty content in the knowledge base.
- **GitHub profile ingestion deferred:** `src/data/github.ts` contains repository types only — there is no GitHub *profile* data source to ingest. The unreachable placeholder processor was removed rather than inventing a profile data model. Live repository metadata is already surfaced by the M09 GitHub service on the project cards.
- **ESLint flat config owns ignore patterns:** `.eslintignore` was removed and its entries moved into `globalIgnores()` in `eslint.config.mjs`. ESLint 9 no longer supports `.eslintignore` and warns on every lint run.
- **The provider interface is free of provider specific types:** `src/lib/llm/provider.ts` declares the contract with plain types and has no imports at all. PRD §49 states that no application level code should depend on Gemini specific APIs, so the Gemini implementation sits behind this boundary and the application only ever sees `LLMProvider`, `GenerationOptions` and `GenerationResult`.
- **The provider interface has `generate()` and `stream()` only:** PRD §49 sketches `embed()` and `moderate()` as well. Embedding is a separate concern that M13.04 already solved, and moderation belongs to the guardrails of M13.07. Declaring methods that no provider would implement would only be an empty promise.
- **The shared helpers moved out of the modules that owned them:** `src/lib/retry.ts` and `src/lib/geminiErrors.ts` are new. The error helpers had to leave `src/lib/gemini.ts`, because that module reads the environment when it is imported and the provider has to be importable without a complete environment. The retry helper had to leave `src/lib/knowledge/embedding.ts`, because the language model layer must not depend on the knowledge base layer. The old import paths still work, so nothing else had to change.
- **`@google/genai` is used instead of `@google/generative-ai`:** The task specification names the older package, but M13.04 already installed the successor because it is the one that can ask for the output dimension the vector column needs. Installing a second Google SDK would double the surface area for no gain.
- **The provider creates its own client:** The client is built from the API key the provider was given and can be injected for the tests. The embedding client is not shared, because it is configured for a different model and lives behind a different module.
- **A timeout belongs to the provider, and it restarts for a stream:** The configured model needs between 13 and 60 seconds for a short question on the free tier, so the default limit is 60 seconds. A streamed answer restarts the limit every time a piece arrives, so a slow first piece is not cut off while a stream that stops producing anything is.
- **A stream is only retried while nothing has been handed over:** Repeating the request after the caller already shows part of the answer would repeat the answer. A failure before the first piece is retried, a failure after it is reported.
- **The API key is removed from every error message:** The provider knows the key, so it removes it from the message before the failure is logged or shown. A test asserts that a rejected key never appears in the message.
- **The thinking budget is a setting of the Gemini adapter, not of the interface:** The configured model spends up to 75 tokens thinking about a question that needs a single number, which is most of the latency and most of the cost. The adapter can turn the thinking off, and the chatbot of M13.09 should do so for the short questions it answers. It stays out of `GenerationOptions` because it is a Gemini concept.
- **The model name stays a configuration value:** PRD §50 asks for the most cost efficient model that still answers well, configured through `GEMINI_MODEL` rather than hard coded.
- **The live language model tests are opt in:** The free tier of the Gemini API allows twenty generation requests a day, and a request over that limit is rejected for the rest of the day. The other live tests in the project make a handful of cheap calls, so they run whenever a key is configured. The language model tests need five generation calls and take a minute, so they only run when `LIVE_LLM_TESTS=1` is set. They are still part of the suite, they just do not spend the daily budget of every `npm test`.
- **The guardrails are keyword based and run before the model is called:** PRD §35 asks for defence in depth, and PRD §39 asks the assistant not to be unnecessarily restrictive. A keyword based classification is fast enough to run on every question, costs nothing, and never has to be retried, which is what a first layer needs. It is a rule set, not a model, so it also cannot be talked out of its answer.
- **A word that only has an innocent reading counts for less:** The topic keywords carry a weight. "specialize" is worth a full signal, "about" is worth half of one, so "what do you think about politics" does not pass as a question about the professional profile while "tell me about his automation experience" still does. Without the weights a single common word was enough to let a question through.
- **A question that only mentions Ankit counts for half a signal:** It is enough in the relaxed profile and not enough in the balanced one. That is what makes the three sensitivity levels mean something different rather than only moving a threshold.
- **The three sensitivity levels change two things:** How much evidence a question needs before it is answered, and whether the attack phrases that also have an innocent reading are acted on. The strict profile acts on them, the balanced and the relaxed one do not.
- **An attempt is told apart from a request for private data:** An attempt that changes the instructions is an injection. A question for a phone number or a private email is a request for something that must not be disclosed. Both are answered with a redirect, but they are reported apart, because one of them is an attack and the other is a normal question about contact details.
- **A request for private data only counts when it is about a person:** "What is an API key" is a technical question and stays allowed. "What is his API key" is a request for a secret and is redirected. Without that rule the assistant would refuse to talk about a subject it is meant to help with.
- **The guardrails compare phrases on tokens instead of with regular expressions:** Every pattern and every text is split into words, so casing, punctuation and spacing do not matter and a phrase that is written as one word is still found. The words of the patterns are split once when the module is loaded, and the text is indexed once per question, so a long question stays fast.
- **The repetitions of the patterns are bounded:** An unbounded repetition in the pattern for an email address makes the pattern go back over the whole text for every position it starts at. A question of a hundred thousand characters took twenty-eight seconds before the repetitions were bounded, and three milliseconds after. The same bound was added to the phone number pattern of the ingestion pipeline, because a long run of digits could slow the check down in the same way.
- **A question longer than two thousand characters is cut off:** A question is a sentence or two, so anything longer is not one. The guardrails do not spend time on it, and the part that is looked at is still checked.
- **The credentials are removed before the phone numbers:** A key often holds a run of digits that the phone number rule would match. Removing the phone numbers first breaks the shape of the key, so the key reaches the visitor with only its first four characters left.
- **The guardrail log never holds the question or the answer:** The event carries the action, the subject, the confidence and how many findings there were. That is enough to see what the guardrails do without keeping the personal data that went through them.
- **The tone of an answer is reported and not changed:** A correct answer with an informal word in it is still a correct answer, so the tone findings are reported instead of acted on. The personal data and the credentials are removed, because those must not leave the server at all.
- **The limits of the chat are kept in memory:** PRD §48 accepts a limit per instance, and the site is meant for low traffic on the free tier. The counts are lost when the instance restarts, and the store is injected so a shared store can replace it without changing the callers.
- **The window of the limit slides:** A request only counts against the half hour it was made in, so a visitor who spreads their questions out is not punished by a fixed boundary. The day works the same way.
- **A request that is turned away is not counted:** Otherwise a visitor who keeps trying while they are blocked keeps pushing their own window further away, and a short wait would not be enough to get them in again.
- **The visitor is the address of the client:** It is taken from the header the hosting platform writes. A visitor who can change that header can get around the limit, so the limit is a guard against accidents and not a wall. The limits are per instance for the same reason.
- **The limits are optional in the environment:** The code holds the values PRD §48 suggests, so a missing variable only means the default is used and an existing deployment does not break. A variable that holds something that is not a number is ignored in the same way.
- **The validation does not show an answer that still holds personal data:** This is the last layer before the answer leaves the server, so it does not try to repair the answer, it sends a safe one instead. An answer that is a little too informal is still shown, because it is still a correct answer.
- **The length limit matches the limit of the model:** The model is asked for at most 1024 tokens, which is roughly four thousand characters, so a legitimate answer never reaches the limit of the validation. An answer above two thousand characters is called long, because PRD §42 asks for concise answers, but it is still shown.
- **The grounding check is a warning:** It compares the numbers and the acronyms of the answer with the context the answer was built from. A warning cannot keep a correct answer from being shown, so the check is allowed to be wrong now and then.
- **The validation runs in the route:** The route is the boundary where the answer leaves the server, so that is where the answer is checked. For a streamed answer the check runs on the final text, which the interface shows in place of the text it streamed.

## Decisions (M19 – Analytics)

- **The configuration of the analytics has one implementation:** The server side module and the browser side module used to carry their own copy of it, and the two could drift apart, so the server could think the analytics were on while the browser thought they were off. The shared module is free of any dependency on the PostHog package, so the browser can read the configuration without pulling a server only package into a client bundle.
- **The analytics credentials are optional:** The analytics layer was written to work in a console only mode, in which the events are written to the terminal in development and nothing leaves the machine. Requiring the credentials in the environment made that mode unreachable, because the environment refused to load before the analytics were ever asked whether they were on. The site now boots without a PostHog project.
- **A value that is still the placeholder counts as no credentials:** The example environment holds `your_posthog_key`. A credential that is a placeholder is not a credential, and a host that is a placeholder is not a host. The old check only asked whether the two values were there, so the layer built a real client and tried to flush to a host that does not exist, which produced an error every nine seconds for as long as the site ran.
- **The host has to be an http or https url:** A value that is not a url cannot be a PostHog host, so it is refused before the client is built rather than after the first flush fails.
- **The credentials are only carried while the analytics are on:** A key that cannot be used is not carried around in the configuration, so it cannot reach a log or a payload by accident.
- **The PostHog client is created through a factory that a test can replace:** The client is held in one place in the module and the package is loaded with a dynamic import, so it never becomes part of a client bundle. The factory follows the pattern of `setLLMProvider` and `setRateLimiter`, and it is the only way the tests get to see the message the module sends.
- **The event is sent in the shape of the installed version of the package:** `posthog-node` v4 takes one message object, `capture({ distinctId, event, properties, timestamp })`. The module was calling `capture(name, properties)`, the shape of version 3, so every event was sent with no name and no identity and none of them ever arrived. A cast on the client hid the mismatch from the type checker, which is why the tests never caught it. The cast is now at the edge of the module, where the package is created, and the shape the module sends is the shape the package takes.
- **The session id is the identity of the event:** PostHog asks who an event belongs to, and the anonymous session id is the only thing that connects the events of one visit without identifying the visitor. The session id stays in the properties as well, so an event can still be found by it.
- **The tracking functions read the configuration from the environment by default:** They used to default to the disabled configuration, so a caller that forgot to pass the configuration sent nothing at all and got no hint about it. The configuration is read when the function is called rather than when the module is loaded, so a change of the environment is picked up without a restart.
- **The events are sent from the server only, and the browser snippet is not used:** The site has a chat field and a field for a job description, where a recruiter types free text that is often confidential to the employer. An automatic capture would record exactly what PRD §36 and PRD §78 tell us not to record, so the events are the deliberate ones the application sends, and the ones the browser sends go through the server side proxy of M19.02. The project key stays on the server and is never published to the page.
- **The session recording is not turned on:** A recording of a visit would show the text a recruiter is typing, which is the same problem the automatic capture would cause, so it stays off.
- **The project is on the EU cloud:** The region only changes the host the events are sent to. The events do not leave the region either way, which is the part that matters for a site that holds professional information.
- **The browser sends its events to the server and not to PostHog:** The project key would have to be published to the page for the browser to reach PostHog on its own. A published key can be read by anyone who looks at the source of the page, and the events of a site can be sent by anyone who copies it. The events go to the server instead, and the server sends them on with the key that never leaves it.
- **The check of the event refuses what it does not know:** Only the event types on a list are accepted, and a field that is not part of the event is refused rather than dropped. A client that tries to send something extra is told that it may not, and nothing a client invents ever reaches the project.
- **The target of a call to action has to be a bare host name:** A host name is a list of labels of letters, digits and dashes joined by dots. The shape does not allow a path, a query, a port or an at sign, so a value that carries an address or a whole path cannot pass as a host name. The host name is brought down to small letters, because that is the form it comes in.
- **The proxy has a limiter of its own:** The events of a visitor are counted under a key of their own, in a store of their own, so a visitor cannot spend the allowance of the chat by clicking a lot of links, and the chat cannot spend the allowance of the proxy. The limit is a hundred events a minute and a thousand a day, which is far above what a visitor can click, and it is fixed in the code because it guards against abuse and not against the cost of the model.
- **A request from another site is refused:** The endpoint writes into the project, so a request from another site would fill the data with events that did not happen here. A browser sends the origin of the page with a request that writes, so a request whose origin is not the site is refused. A request without an origin is allowed, because that is a request that did not come from a browser.
- **The event is flushed before the answer goes out:** The client queues the events and sends them on its own interval, which is the right shape for a process that stays alive. A serverless function is put to sleep as soon as it has answered, so an event that is still queued when the answer goes out can be lost. The proxy flushes the event, so it is sent before the answer. The other routes have not been changed yet, because they are not the task of this milestone, and the change matters from the production deployment onwards.
- **The check of the event lives in the library and not in the route:** The routes import their modules with the path alias, which the test runner cannot resolve, so a route cannot be loaded by a test. The parts that can be checked on their own therefore live in `src/lib/analytics/proxy.ts`, and the route only turns the answer into a response. This is the same shape as the contact form, where the validation lives in `src/lib/contact/validation.ts`.
- **A failure of the sending does not show its reason:** The answer says that something went wrong and nothing more. The reason may hold something about the server that a visitor has no use for, and the server writes it to its own log.
- **The browser sends the events even when it cannot see the credentials:** The browser never holds the project key, so it cannot know whether the server will forward the events. The old behaviour was to turn the analytics off in the browser, which meant the click of a call to action was never counted at all. The browser now sends the event to the server of the site, and the server decides whether it is forwarded. A server without the credentials simply forwards nothing, so the outcome the task asks for is reached on the server, where the credentials are.
- **The browser does not send a timestamp:** The proxy refuses a field that is not part of the event, so a timestamp in the body would be answered with a refusal. The moment the event happened is put on it by the server, which has the clock that counts. The clock of the browser is not trusted, and the visitor can set it.
- **The session of the browser is kept in the storage of the tab:** A visitor who reloads the page is still in the same session, and the events of one visit belong together. The storage of the browser can be refused, in a private window for example, and then the session is kept in memory for as long as the page is open.
- **The click of a call to action is not awaited:** The click opens a link, so the visitor must not wait for the analytics before the link opens. The request is sent and left alone, and the browser is told to keep it alive, so the event still goes out when the page goes away. Nothing in the path of the visitor ever throws, because an analytics failure is not worth an error in the page of the visitor.
- **The host of the site is read through a helper that cannot fail:** The address of the site comes from the environment, and while a project is being set up the value there can be a placeholder such as `your_site_url`. The two calls to action that point at the site used to read the host with `new URL()` directly, which threw on such a value, so the click of the visitor did nothing and the event was never sent. The helper reads the host when it can and falls back to the known address when it cannot, so a setting that has not been filled in never breaks a click.
- **The event of a refused request is sent before the answer goes out:** A visitor that is refused is still a visitor, and the refusals have to be seen next to the requests that were let through. The event is put on the queue of the client of PostHog before the answer goes out, so a serverless function that is put to sleep as soon as it has answered does not lose it. The event carries only the scope, the part of the site and the wait, which the visitor already sees in the headers of the answer, and never the limits themselves.
- **The session of the visitor is worked out before the limit is checked:** The event of a refusal belongs to a session, and the session is worked out from the headers of the request. It is worked out before the limit is looked at, because the request that is refused still has to be counted, and its event still has to carry the session it belongs to.
- **The event of a refusal is built in the library and not in the route:** The routes import their modules with the path alias, which the test runner cannot resolve, so a route cannot be loaded by a test. The part that can be checked on its own lives in `src/lib/analytics/rateLimit.ts`, and the route only says which part of the site was asked for and hands over what the limiter decided. This is the same shape as the proxy of M19.02 and the validation of the contact form.
- **The start of a chat is remembered on its own:** The session of a visitor is shared by the whole site, so the session alone cannot say whether the chat of the visitor has begun. A visitor that fills in the contact form before asking a question would otherwise never be counted as the beginning of a chat. The sessions whose chat has begun are remembered separately, in the memory of the process, as the sessions themselves are.
- **The feedback carries the session of the visitor:** The feedback belongs to the conversation it was given on. It used to carry a session of its own, made for that one request, which put the feedback apart from the questions and the answers it is about. It now carries the session of the visitor, so the feedback can be found next to the answer it is about.

## Decisions (M20 – Monitoring)

- **The SDK is `@sentry/nextjs` in the version 11.10.0:** It is the one package that covers the browser, the server and the edge, and it is the only one that uses the `instrumentation.ts` hook of Next.js 16 on its own. It declares that it supports `next: "^14.0 || ^15.0.0-rc.0 || ^16.0.0-0"`, and the version of Next.js in this repository is 16.3.2. A version that does not support Next.js 16 would not be acceptable, and a second SDK is not used either. The newest version on the page was not taken on faith: the support was read before the package was installed.
- **The configuration of the server lives in `register()` and not in a `sentry.server.config.ts` file:** The installed version of the SDK says so itself. It warns at the build that such a file is an outdated configuration and asks for its content to be put into the `register()` function of the instrumentation file, because `Sentry.init` has to be called inside an instrumentation file. The written task of M20.01 named the two configuration files, and it was written before the version of the SDK was known; the convention of the installed version won, because a file the SDK calls outdated is not a file to keep.
- **The monitoring is optional in the environment, the same way the analytics are:** A missing DSN means the monitoring is off, a value that is still the placeholder of `.env.example` counts as no DSN, and a DSN that is not an http or https URL is refused before a client is built rather than after the first report fails. The site boots, builds and answers without a monitoring project and reports no error of the SDK.
- **The SDK never gets the personal data of the visitor:** `sendDefaultPii` is false in the options of both sides, so the SDK does not attach the body of a request, the cookies or the address of a visitor on its own. The session recording is off as well, because a recording would show what a recruiter is typing into the chat and into the field of the job description, which is the same reason the recording of PostHog is off.
- **The tracing is off:** The performance of M20.06 is a deliberate measurement of the requests that are too slow, and not a span for every request. The tracing of the SDK would cost a quota of the free tier on a site with low traffic, and it would buy nothing here.
- **The SDK of the browser is loaded on its own:** It weighs about a hundred and fifty kilobytes gzipped. It is fetched with a dynamic import, so it is not part of the first load of a page and the page never waits for it, and when there is no DSN the chunk is never fetched at all. A static import would have put a hundred and twenty five kilobytes into the first load, which is a growth PRD §74 would notice. The price is that the SDK is ready a moment after the page is there, and that a failure of the very first moment is not seen.
- **The source maps of the browser are kept:** The SDK deletes them once they have been uploaded, and the upload only happens when there is a key of the project. The deletion runs whatever happened to the upload, so without this the maps would be deleted by a build that never uploaded them and a failure in the production could not be read.
- **The build does not send anything about itself:** The telemetry of the plugin of the build is turned off. It holds nothing private, but the site keeps its data to itself and the statistics of the build are not needed.
- **The browser has a DSN of its own:** `NEXT_PUBLIC_SENTRY_DSN` is a public variable, because a DSN of Sentry is not a secret. It is written in the page by design and only allows sending events to the project it belongs to. The key of the project is a different thing, it never leaves the server and it is not in the page. The server keeps its DSN in `SENTRY_DSN`, which is not published.
- **The variables of the monitoring and of the rate limit store are optional:** `SENTRY_DSN`, `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` were required by the environment although nothing in the code read them, so the site refused to boot unless three placeholders were filled in. PRD's _Environment variables_ section says that only the variables the implementation needs should be present, and a variable that nothing reads must not stop the site from booting. The two variables of Upstash are optional as well, because no milestone has reached the store that would use them.
- **The scrubbing is a layer of its own and everything goes through it:** A failure arrives with whatever the caller passed, so it has to be taken apart. `src/lib/monitoring/scrub.ts` holds the one implementation, and the SDK runs it on every event through the `beforeSend` hook of both sides. A capture path that is added later cannot bypass it by accident, because the hook is on the way out of the process and not on the way into a function
- **The safe shape is built by an allow list:** The parts that are known to be safe are kept and a part that is not on the list does not reach the service, so a field that nobody thought of is not sent by accident. The same rule the guardrails of M13 follow for what they write
- **The parts the SDK builds itself keep every field, and only their strings are cleaned:** The deny list of the private fields applies to the free form parts only (`extra`, `breadcrumbs`, `tags`), because a field of the shape of the site means what it means in a body of a request and nothing anywhere else. The name of the SDK is the name of the SDK and not the name of a recruiter, so `sdk.name` stays. The user of a visitor is not on the list of the safe parts and is never sent
- **The list of the secrets is curated, and not the rule of the guardrails:** The guardrails treat every name with an underscore as a secret, because they read assignments of a text. That rule cannot be used here: the value of a limit such as `RATE_LIMIT_MAX_REQUESTS` is the number twenty, and removing that number from every message would be worse than useless. The monitoring holds the eleven variables of the site that hold a credential. A secret shorter than eight characters is not looked for either, for the same reason
- **The hook of `beforeSend` takes the event alone:** The SDK calls the hook with the event and a hint. The hint is not a list of secrets, and handing the scrubbing to the SDK directly put the hint in the place of the secrets, so the scrubbing failed and every report was lost. The hook takes the event alone, and the scrubbing ignores a second argument that is not a list, so the mistake cannot be made twice
- **A failure of the scrubbing does not send the event unchecked, and it does not lose it either:** The event is never sent as it came, because it may hold something private. A safe shape takes its place instead, with the identity of the event and a note that says the scrubbing failed, so the report survives and the failure of the scrubbing is itself visible
- **The capture is one module and every route hands over to it:** `src/lib/monitoring/capture.ts` holds `captureException()` and `captureMessage()`, and the client of the SDK is created through a factory that a test can replace, the same way the analytics of M19 create the client of PostHog. A route that catches a failure hands it over and holds nothing else, so a route that is added later cannot reach the monitoring service by another way
- **The console line is written by the capture, with the words each route used:** The routes wrote their own line to the console before, and the line is read by the person who works on the site. The capture writes it now, with the same words for each route, so the log looks the way it always looked and there is one line for a failure instead of two
- **The report is grouped by the kind of the failure and by the route:** The fingerprint of the SDK is the grouping of a report, and it holds the kind and the route only. The identifier of the query and the moment are not part of it, because a fingerprint that changes every time opens an issue of its own every time
- **The integration of the console and the integration of the duplicates are left out of the SDK:** The integration of the console writes the console of the site into the report as a breadcrumb, and the console of the site writes the address of a visitor (the line of the limiter) and the failure as it came (the line of the monitoring). The integration of the duplicates drops the second of two failures that look the same, and every failure that the routes catch has to be reported. The console stays in the log of the machine, which is where it is read
- **The message of the parser of a body is not in the report:** The error of the parser holds the first words of the body it could not read, and a report must not hold the text of a visitor. The name of the error and the place it happened are kept, because they are what the owner needs, and the words of the parser are of no use to anyone. The line of the local log still holds the failure as it came, so the person who works on the site loses nothing
- **The address of the visitor is a header that is never sent:** The limiter of the routes counts the requests under it, and the SDK attaches the headers of the request to the report. `x-forwarded-for`, `x-real-ip` and `forwarded` are dropped like the headers that carry a secret, because the address of a visitor is a personal detail
- **The allow list of the scrubbing holds the fingerprint of the SDK:** The list was written before anything set a fingerprint, and the fingerprint was left out of it, so the grouping of the reports was lost on the way out while the reports were still grouped by the kind. A part of the event that the SDK builds itself and that holds nothing private is on the list
- **The proxy of the analytics reports a failure and then lets it go on:** The answer the visitor receives is the one of today, and the framework reports the failure a second time with the context of the request. The two reports are grouped under the same issue by the fingerprint
- **The browser capture will need its own client:** The capture loads the package of the SDK with a dynamic import, which is what the server needs. The browser already holds the SDK of M20.01, and M20.07 will hand that one to the capture through the factory instead of loading the package a second time in the page
- **The classification of a failure of the model uses the status, the name of the error and the reason of the API, and never the text of the message:** The text of the message of the API can be anything, and a rule that reads it would classify a failure by the wording of the API rather than by what happened. The reason is a fixed word of the API (`API_KEY_INVALID`, `safety`, `blocklist`) and not a text, and it is what tells a request the API refused for its own reasons from a request it refused because the key is wrong: both of them are a 400. The mapping is: 429 is `quota`, 408 is `timeout`, 5xx is `unavailable`, 401, 403 and 404 are `configuration`, 400 is `unknown`, and the reasons of the API are read before the status
- **The failure carries the reason of the API, so `LLMError` and `readErrorDetails()` changed:** The reason was in the body of the answer of the API and was thrown away when the adapter of the provider replaced the body with its own message. Without it a refusal of the model and a wrong key are the same 400 and cannot be told apart. `LLMError` holds the reason and `readErrorDetails()` gives it back, and the adapter passes it through. The three files were not in the list of the task of M20.04, because the task was written before it was known that the status alone is not enough. The raw body of the embedding path still loses the reason, because the embedding client builds its own message and not the one of the adapter
- **The report of a failure of the model is grouped by the kind alone:** The fingerprint of a failure of the model holds the kind and nothing else, so a thousand timeouts are one issue and not a thousand. The reports of the routes keep the kind and the route, because the same failure of the model in two routes is two different problems
- **The place where the failure happens reports it, and the route that catches it afterwards does not:** The failure of the model is reported by the orchestration, which knows the kind of it. The route that catches it afterwards writes the line of the local log, which is what it always did, and leaves the report to the place that knows the kind of it. The capture marks a failure as reported before its first wait, so the route sees the mark even when it catches the failure in the same tick
- **The report of the model is not awaited:** The visitor gets the friendly answer as soon as the failure is known, and the report goes out on its own. The report is still flushed by the capture before the answer of the route goes out, so it is not lost when the instance is put to sleep
- **The model name comes from the environment and not from the validating module:** The monitoring layer does not import `src/lib/env.ts`, because that module refuses to load without a complete environment and the monitoring has to be able to load without one. The variable of the environment is the source of truth in both places: the factory of the provider hands `GEMINI_MODEL` to the API and the report holds the same name
- **A failure of a service is grouped by the name of the service and by the kind of the failure, and never by the repository:** An outage of the GitHub API would otherwise open an issue of its own for every repository of the site, and a page of the projects has six of them. The fingerprint of the report holds the service and the kind and nothing else, so an outage is one issue. The name of the repository is in the report and not in the grouping
- **The report of a service is a message and not a failure, and it carries a level:** A service that could not be reached while the site kept working is not an exception of the site, and the SDK has a way to report such a thing as a message. The SDK gives a message the level "info" when nothing else is said, and a report of the level "info" is not one that can be alerted on, so the level is part of the context of the report now: a warning when the site answered with what it had, an error when the failure reached the visitor
- **The safe shape of a failure holds the tags, the fingerprint and the level of a report:** A report that is not of a route has to say what it is about and how it is grouped, and the shape of M20.02 had no place for either. The extension is additive: the reports of the routes carry no tags and no fingerprint of their own, so they are exactly the ones they were
- **The text of a report of a message was never delivered, and the allow-list of M20.02 was missing it:** The allow-list held the parts of an event of the SDK that are worth reporting, and `message` and `logentry` were not in it, so the hook of `beforeSend` took the text away from every report of `captureMessage`. It was found when M20.05 sent its first report and read as nothing at all. Both keys are in the list now, and the text is cleaned of its private parts like any other text
- **The failures of one repository are counted and one report goes out per window:** The count of the failures is added to the report that follows, so the first report goes out at once and the next one says how many failures piled up. The map is held in the memory of the process, the same way the limiter of the chat is held, and the window is five minutes
- **The message of the database is read to decide the kind of the failure and is never reported:** The message of PostgreSQL can name a table, a column or a constraint. Only the fixed words of it are read, so the kind can be told apart, and only the kind is reported. The whole message stays in the log of the server
- **The GitHub service answers with what it had, and the report says so:** The task specification of M20.05 says that the service answers with the cached data when the fetch fails, and that the report says that the cache answered. The service does not: it answers with nothing and the card shows the placeholders of the numbers, because it was written that way on 2026-10-22 and the specification was written on 2026-11-04. The behaviour of the cache was not changed, because it is out of the scope of the task and because the site must behave exactly as it did before. The report says that the site answered with what it had, which is true: the page keeps working and only the numbers of the repository are missing
- **The performance is watched with a threshold and the tracing of the SDK stays off:** The two ways of watching the performance are a threshold and a span for every request. The tracing is the richer answer and it costs a span per request, which on a free tier is a quota that the traffic of a site nobody visits spends. A site with low traffic does not need a picture of the performance, it needs to know when something is broken, and the threshold is the shape that fits the rest of the milestone: a report that arrives when something is wrong rather than a stream of data that has to be looked at. The tracing is off in the options of the SDK of M20.01 and it stays off. Turning it on is a change of the configuration of the SDK and not a change of the code of the site, and the owner can make it when the traffic of the site is worth a picture of it
- **The thresholds are optional and a wrong value is ignored rather than refused:** The variables of the environment of the thresholds are declared in the schema of `src/lib/env.ts` with a rule of their own, because a value that is not a number has to mean the default of the code and not a site that does not boot. The other optional numbers of the environment are refused by the schema, so a wrong value of a limit stops the site. The thresholds are read the other way round, because the cost of a wrong threshold is a report that is not sent and the cost of a wrong limit is a limit that is not the one the owner meant
- **The clock and the reporter of the measurement are injected:** The rule of the limiter of the chat, whose store is injected for the same reason, is the model. A test says that an operation took two thousand milliseconds without waiting two seconds, and a test sees the reports without a monitoring service
- **The report of a slow operation is a message and not a failure:** A request that is slow is not an exception of the site, and the site still answered. The report is grouped by the name of the operation, so a slow answer every day is one issue and not a hundred, and it is of the level "warning", because a report of the level "info" cannot be alerted on
- **The generation and the retrieval are reported apart:** The orchestrator knows both numbers already. Reporting them apart tells the owner whether to look at the model or at the database, which is the difference between a slow answer and a slow knowledge base
- **The report of a boundary holds no message of the failure:** The message of a failure can hold the text of the page and the value of a field, and a visitor who sees a page that failed must not read a text of the site. The report says what happened in a fixed sentence and it keeps the name of the error and the frames of the stack, because a name is the name of a class of code and a frame is a place in the code. The line of the local log holds the failure as it came, so the person who works on the site loses nothing, exactly as it was decided for the message of the parser of a body in M20.02
- **The digest of Next.js is its own field and it is cleaned like an identifier:** The digest is the tie between the failure in the browser and the one on the server, so it has to arrive. It is a hash and it cannot hold personal data, but it is a number, and a long number looks like a phone number to the redaction of the personal data, which took it apart and left `[REDACTED]` in its place. The digest is therefore its own part of the shape of a failure, it is cleaned of the secrets of the environment and of nothing else, and it is only read when it has the shape of a digest, so a text in that place is still cleaned like any other text
- **The SDK of the browser is handed to the capture through the factory:** The capture loads the package of the SDK with a dynamic import, which is what the server needs. The browser already holds the SDK of M20.01, so loading the package a second time in the page would cost the weight of the SDK for nothing. The decision that was taken in M20.03 is carried out: the file of the browser hands the SDK it loaded to the factory of the capture, and the capture uses the one that is already there
- **The page of a boundary does not depend on the theme of the site:** The boundary of the root replaces the layout of the site, and the provider of the theme lives in that layout. A page that asked for the theme of the site would fail in the boundary of the root, and a failure of the boundary of the root has nowhere to go. The colours of the page are the ones of the design system and they follow the class of the site when it has one, and the colour of the machine when it has none, which is what the documentation of Next.js asks for
- **The two boundaries show the same page, and the page is a component of its own:** The boundary of the routes and the boundary of the root show the same thing to a visitor, so they show the same component. The component is in `src/components/layout/`, next to the other parts of the page, and it holds no state and no logic of the monitoring: the boundary reports the failure and the component shows it
- **The report that a failure produces is built by the capture of the site and caught before it is sent:** The rules of the privacy have to be checked against the very payload that the service would receive, and not against a copy of it that the script made up. The capture of the site has a factory for the client of the monitoring, and the script puts a client there that keeps what it is given. The address of the service is a fake one while the cases run, so nothing leaves the machine even if a report is missed, and the real address is put back for the one real report that shows the connection with the service works
- **The rules of the privacy are checked on every payload, and not only on the ones of a case that asks for them:** The rules are the ones of PRD §79, and they hold for every report the site sends and not only for the reports of a case. The identifiers are left out of the text that the rules look at: the digest is a hash and it cannot hold personal data, but it is a number, and a number of ten digits looks like a number of a phone
- **The script never writes the value it found:** A rule that fails prints the name of the rule and a short description of what it found, and never the value it found, because the report of the script is read by a person and is kept in a file. The line of the local log of the site is quiet while the cases run, so the report of the script is the report of the rules and not a copy of the log
- **The live part of the failures of the model is opt-in with `LIVE_LLM_TESTS=1`:** The free tier of the model allows a few requests a day, and a failure of the model is made by pointing the environment at a name that does not exist. The rule is the same as the one of the live tests of the model, and the case is skipped with a note when the flag is not given
- **The account is the owner's and the script does the part the API can do:** The project of Sentry is created with the API, with the platform of Next.js and with the rule of the new issue turned on, and the address of the service is written into `.env.local` and nowhere else. The token is never in the chat and never in the repository: it is put in `.env.local` and the script reads it from there. The rules of the alerts are made by hand, because the page of the project is the place where they are made
- **The environments are named by the site and not by the service:** The site names them itself, `production` when it runs for the visitors and `development` when it runs on a machine of a person, and the service makes an environment the first time a failure arrives with that name. The names are in one place, the configuration of the monitoring, so the two can never disagree
- **The focus is moved to the way to try again:** The specification of M20.07 and PRD §71 ask for it, and a visitor who cannot see the page is taken to the only thing that can be done with a keyboard. The ring of the focus is the colour of the text of the page, so it is seen in both the light theme and the dark one
